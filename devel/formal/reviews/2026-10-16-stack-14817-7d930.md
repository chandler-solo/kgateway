## P1 — A queued KRT candidate acquires the new connection's generation

The new fence correctly rejects a publisher already holding the gate when a
new connection starts. It does not establish the origin of a candidate that
enters the gate later. The ordinary handler still publishes
[`e.Latest()`](https://github.com/kgateway-dev/kgateway/blob/7d930bb2183b90343f9613f03dcd345973fc9f38/pkg/kgateway/proxy_syncer/proxy_syncer.go#L551-L557)
from a queued event, while the admission hook independently reads and publishes
[the collection's current row](https://github.com/kgateway-dev/kgateway/blob/7d930bb2183b90343f9613f03dcd345973fc9f38/pkg/kgateway/proxy_syncer/proxy_syncer.go#L299-L312).
At installation the fence receives
[`g.connGen[proxyKey]`](https://github.com/kgateway-dev/kgateway/blob/7d930bb2183b90343f9613f03dcd345973fc9f38/pkg/kgateway/proxy_syncer/publish_gate.go#L342-L347),
which now describes the new connection, not the old event's provenance.

The new regression executes this schedule:

1. A real KRT event callback receives `queued-old` and pauses immediately before
   its production `syncXds` call. This represents a scheduling delay, not a
   reordered KRT event stream.
2. The collection advances to `current-deferred`; `GetKey` returns that row
   while the old callback is paused.
3. The old stream closes. Real admission callbacks start a new generation,
   clear the cache and offer the current deferred row. There is correctly no
   installed snapshot on the new connection yet.
4. A fresh RDS watch is registered. The old callback resumes and uses the
   gate's newly adopted generation, so the old candidate installs and answers
   that watch with `queued-old`.
5. The subsequent current event also executes. Its newly referenced missing
   assignment makes it resolve against the stale publication and hold the
   route flip, instead of undoing the stale response immediately.

**Evidence: executed Go/cache counterexample and a bounded formal
counterexample.** `TestReviewQueuedCandidateCannotCrossReconnect` fails at the
designated response-version assertion on the pristine production source and
in all three race-enabled repetitions, without a race-detector report.
`QueuedPublicationLateStampBug` violates `NoObsoleteCandidateResponse`.
This is a protocol-ordering defect even though memory accesses are synchronized.
It is not restricted to REFERENCED mode.

The response can roll a returning proxy toward an older configuration while
the authoritative candidate is withheld. Actual Envoy application of this
new schedule was not measured, so this report does not claim an observed
traffic outage or policy bypass. The old revision's live rollback remains
separate evidence.

**Recommended change:** order admission replay, ordinary KRT updates/deletes
and timer work through one per-key publication protocol. Carry candidate
generation/revision provenance from selection or enqueue, and validate it at
the publication boundary. Alternatively, resolve authoritative current state
inside a properly synchronized publication transaction. Sampling the current
generation after an old event leaves its queue is too late. Preserve the
existing gate/client-state/fence/cache lock order and shared-key semantics.

The proposed `QueuedPublicationCapturedOrigin` abstraction passes safety and
conditional eventual-send checks over eighteen states. It illustrates this
specific repair obligation; it does not establish ordering of all
same-generation revisions, deletion/recreation, multiple streams or the two
separately locked phases of `connectionStarted`.

## P2 — Coherent recovery leaves the previous carry deadline behind

[`publishLocked`](https://github.com/kgateway-dev/kgateway/blob/7d930bb2183b90343f9613f03dcd345973fc9f38/pkg/kgateway/proxy_syncer/publish_gate.go#L394-L410)
cancels the carry timer but leaves `carriedSince` intact. Cleanup when a cluster
reappears exists in
[`boundCarryLocked`](https://github.com/kgateway-dev/kgateway/blob/7d930bb2183b90343f9613f03dcd345973fc9f38/pkg/kgateway/proxy_syncer/publish_gate.go#L1116-L1150),
which the coherent publication path does not call. A later disappearance can
therefore inherit a deadline from a resolved episode.

The test publishes cluster A, temporarily carries A, publishes a coherent
recovery, waits beyond the *old* carry deadline while A is present, then
publishes a second candidate missing A. A disappears from the cache
immediately, although the second episode has just begun. The test uses a
100 ms bound and 150 ms healthy interval; the configured product default is
ten minutes. This is premature expiry on a second episode, not failure of the
new quiescent-expiry timer.

**Evidence: executed Go/cache counterexample and a bounded formal
counterexample.** `TestReviewRecoveryStartsFreshCarryEpisode` fails at the
designated cluster-retention assertion, including three race-enabled
repetitions. `CarryEpisodesRecoveryBug` finds the corresponding six-state
history. A short translation gap after recovery can now remove the last good
cluster and endpoints immediately, exposing routes to avoidable failure until
recovery; traffic impact is inferred from the missing dependency, not measured
in this probe.

**Recommended change:** reconcile carry membership and episode start times on
every candidate path, including coherent recovery, reference removal and
coherent held publications. End only the episodes that resolved. Do not
unconditionally clear all ages inside `publishLocked`: deferred publication
also uses it, and that would keep restarting unresolved clusters' deadlines.
Retain the new timer and its stale-callback protection.

`CarryEpisodesReset` passes the fresh-episode invariant and quiet-expiry
temporal property over eighty-two states, assuming weak fairness of time
advancement and expiry. That finite result is not a Go scheduling or wall-clock
guarantee.
